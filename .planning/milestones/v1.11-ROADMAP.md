### Phase 32: WordPress registry icon set

A third tab in the icon picker, **WordPress**, offering every icon registered
with core's icon registry (core's own library plus any collection a plugin
registers). Shown only where `wp_get_icon()` exists (WordPress 7.1+); Maestro
still supports 6.4+.

Measured on 7.1.3 (2026-10-28): core registers 88 icons in one `core`
collection (label "WordPress") on `init`. The registry sanitises every icon to
`<svg>`, `<path>` and `<polygon>` with kses, so each is monochrome path data,
a good fit for 1.10's mask path. `WP_Icons_Registry::get_registered_icons()`
and `WP_Icon_Collections_Registry::get_all_registered()` are public.

Design:

- **Stored value is a data URI**, like Bootstrap: `wp_get_icon( $name,
  array( 'size' => null ) )`, given the same `fill="#a7aaad"` Bootstrap bakes in
  (the no-mask fallback colour), base64-encoded. Nothing new in the schema,
  `Config::sanitize_icon()`, Replay's mask path or export/import. A saved icon
  keeps rendering if the registering plugin is later removed.
- **Delivered on demand,** like Bootstrap: a `GET maestro/v1/icons` route
  (same `capability()` gate as `/config`) returns `{ icons: [ {label, terms,
  src} ] }`, the Bootstrap file's shape, so the picker's `loadSet()` is reused.
  The picker sends the existing `wp_rest` nonce. Inline would add ~50 KB to
  every edit-mode page.
- **Icons over `Config::MAX_DATA_URI_BYTES`** or that do not produce an
  `<svg>` are skipped rather than offered and then refused on save.
- **`iconSet` = `registry`** for a stored icon that matches a registry icon,
  so the picker opens on that tab. Checked only when the icon is an SVG data
  URI that is not a Bootstrap icon, and only on 7.1+.
- **Search terms** include the icon name, label and collection label. Icons
  from a non-core collection show the collection in their tooltip.

Must be true:

- Below 7.1 the tab is absent and nothing else changes.
- Every offered `src` passes `Config::sanitize_icon()` unchanged.
- An icon registered by a plugin appears; an unregistered one does not.
- Choosing a registry icon saves, survives reload, colours with the admin
  scheme (mask), and reopens the picker on the WordPress tab.
- The route refuses users without `capability()`.

Tests: integration (`IconSetsTest` additions, route auth, a plugin-registered
icon), JS unit for nothing new (the picker reuses `loadSet`), e2e: open the
WordPress tab, choose an icon, reload.

Not proven by automation: how core's 24-px-grid icons look beside 20-px
Dashicons (they draw smaller). Dan eyeballs it; a viewBox crop is the fallback
if they read too small.

### Phase 33: Separator polish

From the 2026-09-22 and 2026-09-23 todos:

1. **Enter no longer lands on Remove.** Selecting a separator focuses its ▲
   (or the row), not Remove separator.
2. **Move obeys the add rule.** Drag and Alt+Arrow refuse a position where
   core would drop the separator (directly next to another separator, or
   last), using the same `canAddSeparatorBelow` logic, with a spoken reason.
3. **Hidden adjacent separator.** Removing a visible separator never
   re-reveals a stored-but-dropped one in the same place (fixed by 2, plus a
   cleanup that drops already-unreachable separators from the payload).
4. **Rule visible on light schemes.** The edit-mode dashed rule takes its
   colour from the menu text colour at low opacity instead of a fixed
   near-white.
5. **Icon-only separator buttons** (approved option 1 + 2's glyph, Dan
   2026-09-23): add both to the icon-only list; Add uses
   `dashicons-editor-insertmore`. Accessible names and tooltips unchanged.

Tests: `carry-separators.test.mjs` cases for 2 and 3; `separators.spec.ts`
for 1, 2 and 5 (axe on the icon-only buttons). Recapture screenshot 1 at
release.

### Phase 34: Stale editor files notice

As designed in the 2026-09-24 todo: the page states `MAESTRO_VERSION` inline;
`maestro.js` sets `window.maestroBuild`; `maestro.css` sets `--maestro-build`;
a mismatch (or a missing value) shows an edit-mode notice with a Reload button
that refetches the stale files with `cache: 'reload'` and then reloads.
`bin/prep-release.sh` bumps both constants and `release.yml` checks them.

Tests: e2e with route interception (stale JS, stale CSS, neither), and no
notice outside edit mode.

### Phase 35: Save-state feedback and announcements

The 2026-08-09 todo predates the floating status (#257/#265), which already
keeps errors on screen. What is still true: after a successful save the
status disappears after 2 s, and each save may be announced twice (the
element is an `aria-live` region **and** `setStatus()` calls `speak()`).

- Keep the floating "Saved" as is; after it fades, leave a muted persistent
  check in the toolbar's status slot with the title "All changes saved", until
  the next change. Nothing is shown before the first save.
- Announce once per save: drop the duplicate path (keep `speak()`, which the
  floating element's show/hide cannot interrupt).

Human check (Phase 36 checklist): VoiceOver says "Saved" once per change.
