<objective>
Run the four judgement gates over the whole release diff: code review,
accessibility, adversarial security, performance.

Purpose: these are the gates that caught real problems in v1.4.0 — a multibyte
truncation that blanked labels, a changelog overclaim, and an a11y defect in the
visibility popover. They run consolidated over the release diff precisely
because per-phase passes miss interactions between phases.
Output: four recorded verdicts with evidence.

**`autonomous: false`** throughout — every gate here is a judgement call.
</objective>

**What this release adds, and therefore what the gates must actually look at:**
- a new stored axis (`hidden_users` / `child_hidden_users`) accepting user IDs
- a widened hide seam with an edit-mode suspension
- an async picker consuming core's `wp/v2/users`
- a server-side `list_users` gate that PRESERVES existing axes for an
  under-privileged saver rather than dropping them

**Known gaps to test against rather than rediscover:**
1. The multisite super-admin exempt branch has NO test (single-site suite).
2. Codex reviewed the implementation at `a1769f9` but NOT the round-2 fixes in
   `23fa96c` — the server-side gate and bounded query are unreviewed by it.
3. The person-picker surfaces (search field, results list, chips, self-target
   caution, limit message) have never had an independent a11y pass. They were
   written to the bar, not audited against it.

**v1.4.0's own a11y finding is the precedent worth remembering:** the visibility
popover's role groups shipped without programmatic group names (WCAG 1.3.1, S1,
serious) and it was this gate that caught it. That popover now has twice as many
groups.

<task type="checkpoint">
  <name>Gate 8: Code review over the full release diff</name>
  <action>
    Review `v1.4.1..main` as one change, not as five plans. The interactions are
    where the risk is: storage ↔ seam ↔ model ↔ client all had to agree on the
    same axis shape, and each was written in a different plan.

    Pay particular attention to the round-2 fixes in `23fa96c` — the server-side
    `list_users` gate and the bounded validation query — since no reviewer has
    seen them. The preserve-don't-drop behaviour in `Config::sanitize()` is
    subtle: confirm it cannot be turned into a way to KEEP a stale rule alive
    that the admin believes they removed.

    Consider one more `@codex review` here; it has found something real on every
    pass so far, including two issues raised against the plans that then shipped
    as live bugs anyway.
  </action>

<task type="checkpoint">
  <name>Gate 9: Accessibility sweep — WCAG 2.2 AA, Default/Modern/Midnight</name>
  <action>
    The person-picker surfaces are new and unaudited. Check specifically:
    - the search field has a programmatic label (it uses screen-reader-text)
    - results are reachable and operable by keyboard, and the list's appearance
      is announced rather than silent
    - each chip's remove control names WHO it removes, not just "remove"
    - the self-target caution and the limit message are announced (both live in
      an aria-live region — confirm it actually fires)
    - focus goes somewhere sensible after adding or removing a chip
    - all four group headings are distinguishable to a screen-reader user
    - contrast holds on all three admin colour schemes, including the amber
      self-target caution

    Test with a real screen reader, not just a static audit. The v1.4.0 S1 was a
    missing programmatic name — the kind of thing an automated checker reports
    but a human dismisses.
  </action>
  <verify><manual>Screen-reader pass on all three schemes; findings triaged by severity.</manual></verify>
  <done>A11y verdict recorded; serious findings fixed before the tag or explicitly deferred with rationale.</done>
</task>

<task type="checkpoint">
  <name>Gate 10: Adversarial security pass</name>
  <action>
    The cosmetic-only invariant is enforced by test, so attack the edges instead:

    - **Enumeration.** Can a Maestro editor WITHOUT `list_users` learn about
      users they shouldn't? The client gate is cosmetic; the server gate is the
      real one. Verify the model does not decorate names for such a user, and
      that a hand-crafted REST POST cannot inject IDs.
    - **Persistence.** Can that same editor destroy an admin's rules? The gate
      preserves rather than drops — confirm preserve is what actually happens on
      a full-replace autosave.
    - **The edit-mode suspension.** It deliberately makes a hide NOT apply in one
      context. Confirm it cannot be reached outside edit mode, and that
      `is_edit_mode()`'s own capability gate is doing the work.
    - **Bounds.** MAX_HIDDEN_USERS, MAX_ITEMS, payload size, and the qualified-key
      entity collision already logged as a known LOW.

    Re-confirm the cosmetic-only invariant holds for the per-user path exactly as
    for roles — that is the claim the whole feature rests on.
  </action>
  <verify><manual>No unaddressed HIGH/MEDIUM; LOWs recorded as todos.</manual></verify>
  <done>Security verdict recorded with the specific checks performed.</done>
</task>

<task type="checkpoint">
  <name>Gate 11: Performance assessment</name>
  <action>
    Two new costs, both bounded by design — verify the bound rather than trust it:
    - the hide seam gained an id-list intersect (trivial, but confirm it does not
      run for configs with no user axis — the fast path exists for that)
    - `get_menu_model()` gained ONE batched name query, and `Config::sanitize()`
      an `include`-bounded validation query (the round-2 fix replaced an
      all-users fetch; confirm the replacement is actually bounded)

    Measure against `docs/performance/config-size-and-page-load.md` rather than
    inventing a new baseline. That doc puts realistic configs at ~0.1 ms/page;
    anything here should be lost in that noise. If it is not, that is the finding.
  </action>
  <verify><manual>Measured numbers recorded against the existing benchmark.</manual></verify>
  <done>Performance verdict recorded with figures, not impressions.</done>
</task>
