Turn the feasibility note's §6 guardrail sketch into a real, enforcing test for the
per-user axis, and settle the two §11/§12 safety rails.

may change, `current_user_can()` may not. Phase 19 gated the feature on that claim being

and a regression test for the anti-lockout rail.

The §6 guardrail sketch, to be implemented literally:
```
STEP 1  baseline    = { cap => current_user_can(cap) for cap in C }   // user U
STEP 2  apply       Config::save( items: { slug: { hidden_users: [U.ID] } } )
STEP 3  ASSERT      { cap => current_user_can(cap) } === baseline      // while active
STEP 4  ASSERT      slug present in get_menu_model() BEFORE, ABSENT after
STEP 5  remove      Config::save( items: {} )
STEP 6  ASSERT      { cap => current_user_can(cap) } === baseline      // after removal
```
C must be the target role's FULL capability list (read it off the live role object —
do not hand-enumerate, or a capability added by a future WP version escapes the net).

VERIFIED FINDING (2026-08-08, this repo @ 81d7ef8) — relevant to Task 3:
Maestro registers NO admin menu page. `grep -rn "add_menu_page|add_submenu_page|
add_options_page|add_management_page" includes/` returns nothing; the editor's only
entry point is an admin-bar node (`includes/class-admin-bar.php:47`), which lives in
`$wp_admin_bar`, NOT in `$menu`/`$submenu`. No `items` rule can address it. The §11
anti-lockout rail is therefore satisfied STRUCTURALLY, not by protective code — so
Task 3 is a regression test that pins that property, not a feature.

<task type="checkpoint" resolved="true">
  <name>Task 2: DECISION — super-admin exemption scope [RULED 2026-08-08: new axis only]</name>
  <ruling>
    **Human ruling, 2026-08-08: option (a) — NEW AXIS ONLY.**

    Super admins are exempt from `hidden_users` / `child_hidden_users`. The shipped
    `hidden_roles` / `child_hidden_roles` axes keep their v1.4.1 behavior exactly: a super
    admin remains subject to a role hide, unchanged.

    The checkpoint is therefore CLOSED — implement (a) directly and do not re-open the
    question. Document the axis asymmetry in the user-facing docs (21-05 Task 3), since it
    is a real behavioral difference a site owner can observe.
  </ruling>
  <files>includes/class-replay.php</files>
  <behavior>
    21-CONTEXT.md locks "super admins exempt from hides by default (multisite §12) — a hide
    never affects a super admin." Taken literally that sentence covers ALL axes, including
    the shipped `hidden_roles`. That reading is a BEHAVIOR CHANGE to v1.4.1: today a super
    admin on multisite IS subject to a role hide, and some existing installs may be relying
    on exactly that to declutter their own network-admin view.

    Two readings, materially different:
    (a) NEW AXIS ONLY — exempt super admins from hidden_users/child_hidden_users; leave the
        role axes exactly as shipped. Zero regression. Cost: an asymmetry between axes that
        has to be documented and explained to users.
    (b) ALL AXES — exempt super admins from every hide. Conceptually cleaner and matches the
        CONTEXT sentence as written. Cost: changes shipped multisite behavior in a minor
        release, silently un-hiding rows for super admins on upgrade.
  </behavior>
  <action>
    RECOMMENDATION: (a), new axis only.

    Rationale: the exemption's stated purpose (§12) is anti-lockout, and there is no lockout
    to prevent — hiding is cosmetic and every hidden page stays URL-reachable by design, as
    Task 1 now proves. So (b) spends a real backward-compatibility break on a hazard that
    does not exist, in a milestone whose zero-regression bar has held through v1.4.1. The
    asymmetry in (a) is a documentation cost, which is recoverable; a silent behavior change
    on upgrade is not.

    Note also that single-site is the primary target: on single-site `is_super_admin()` is
    true for any user with `manage_network`-equivalent standing, which in practice means the
    admin. Under (b) an admin could not hide anything from themselves — which directly
    contradicts the locked "self-target = warn but allow" decision in 21-CONTEXT.md. That
    contradiction is itself a strong argument for (a), and it should be raised at the
    checkpoint because it means (b) is not merely riskier but internally inconsistent with
    another locked decision.

    STOP HERE. Present both readings and this analysis; implement only after a human ruling.
  </action>
  <verify>
    <manual>Human confirms the exemption scope before any code lands.</manual>
  </verify>
  <done>Scope decided and recorded in the phase summary with rationale; implemented per the ruling; multisite behavior covered by a test if the environment supports it, or the gap explicitly documented if it does not.</done>
</task>
