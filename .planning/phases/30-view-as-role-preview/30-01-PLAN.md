## The window

Core decides the menu between two points of every `wp-admin/admin.php` load
(WordPress 7.1, checked 2026-10-23):

1. **Start:** `auth_redirect()` (admin.php line 104) fires the `auth_redirect`
   action for a logged-in user. Nothing between it and the `menu.php`
   require (line 163) checks a capability.
2. Core's items are added in `wp-admin/menu.php`, plugins add theirs on
   `_admin_menu` / `admin_menu`, Maestro's `replay()` runs at `admin_menu`
   `PHP_INT_MAX`, and `wp-admin/includes/menu.php` prunes with
   `current_user_can()` (lines 89 and 176).
3. **End:** `custom_menu_order` is applied unconditionally at line 291. The
   filter is removed there, at `PHP_INT_MAX`, after Maestro's own callback.
   `user_can_access_admin_page()` is at line 375; the page's own callbacks
   come later still.

Belt and braces: `admin_init` also ends the window, so a page that somehow
skips the menu include still runs as the real viewer from `admin_init` on.

**Revised during execution (2026-10-23): Dashboard only.** Core's pruning
records what it removed in `$_wp_menu_nopriv` / `$_wp_submenu_nopriv`, and
user_can_access_admin_page() reads them after the window. Built inside the
window they describe the role, so an administrator previewing Editor on
Settings was refused the page (seen on a real request). They cannot be rebuilt
for the viewer once the rows are gone, and clearing them could let through a
page the viewer really lacks. The Dashboard needs only `read`, so preview runs
there and is refused elsewhere (`not_dashboard`), and roles without `read` are
refused (`role_cannot_read`).

## Tasks

1. **`Preview` request validation (unit, test first).** A pure
   `Preview::validate( array $request, array $env )` returns either
   `array( 'role' => ... )` or `array( 'refused' => reason )`. Reasons:
   `no_capability`, `bad_nonce`, `unknown_role`, `super_admin`,
   `outside_site_admin`, `not_admin_page` (AJAX, REST, cron). The role is read
   with `sanitize_key()`. Unit tests cover every branch.
2. **The filter (integration, test first).** `Preview::subtract( $allcaps,
   $caps, $args, $user )` returns `$allcaps` unchanged unless the window is
   open and `$user->ID` is the viewer; then every granted key the role lacks
   becomes `false`. It never adds or sets `true`. Tests:
   - subtraction: an administrator previewing Editor loses `manage_options`,
     keeps `edit_posts`;
   - never grants: a custom-role viewer previewing Administrator gains nothing;
   - isolation: another user's checks during the window are untouched;
   - cleanup: after `custom_menu_order` (and after `admin_init`) the viewer's
     checks are real again, and `user_can_access_admin_page()` sees real caps;
   - authorization: no filter for a viewer without `capability()`, with a bad
     or missing nonce, an unknown role, or as a multisite super admin.
3. **Replay seam.** `is_hidden_for_current_user()` reads the previewed role for
   Term 1 and skips Terms 2 and 3 while previewing. `is_edit_mode()` is false
   while previewing, so the editor never loads.
4. **Parity.** Core's `wp-admin/includes/menu.php` is `require_once` and
   declares functions, so it can run only once per PHP process. The
   integration suite runs it once (Editor) to prove the window closes inside
   it and the Dashboard stays reachable. The per-role comparison against real
   users of each core role moves to 30-02's e2e, where every request is a fresh
   process.
5. **No writes.** The preview path calls no `update_option`, `update_user_meta`
   or `Config::save()`. Asserted by counting option and user-meta writes
   across a preview request.
