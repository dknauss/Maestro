<objective>
De-hardcode the menu column width — independently of any storage or settings
work — by MEASURING it rather than assuming it.

Purpose: this is shippable on its own and fixes a live defect. On a site where
another plugin widens the menu (Keel and PX both do, with `!important` from
961px), edit mode forces `left: 160px` on the toolbar, so the toolbar covers the
right edge of the menu being edited. Reproduced in wp-env on 2026-09-15 with Keel
at 240px: `#adminmenuwrap` 240px, toolbar left edge 160px.

**Revised 2026-09-21.** The original plan made the width a custom property with a
160px default that later plans would fill from stored config. A stored value
cannot know about another plugin's width, so it would replace one wrong
assumption with another. Measuring the rendered menu is correct for core, for
Keel/PX, and — later — for Maestro's own `menu_width`, with no special case for
any of them.

**Collapse control: superseded.** Task 2 of the original plan (make
`#collapse-menu` visibly `aria-disabled`) was overtaken by UX-12, shipped in
1.5.3: the control is hidden during edit mode and removed from the tab order
(`maestro.css`, "UX-12 — withdraw controls that edit mode has made inert"), on
the reasoning that a control that cannot act should not be offered. That is a
later, shipped, deliberate decision; this plan does not re-open it. Forced unfold
itself is unchanged: **keep forcing unfold** still stands.
</objective>

**The three hardcoded values** (re-verified 2026-09-21 against `main`):

| Location | Rule | Role |
|---|---|---|
| `maestro.css:22` | `width: 160px !important` | unfold backstop on `#adminmenu`/`#adminmenuwrap`/`#adminmenuback` |
| `maestro.css:28` | `margin-left: 160px !important` | matching offset on `#wpcontent`/`#wpfooter` |
| `maestro.css:523` | `left: 160px` | the toolbar's left edge — "clears the admin menu column" |

**What other plugins do** (Keel `keel_defaults_admin_menu_width_css()`; PX
`get_admin_menu_width_css()` — same rule): inside `@media screen and
(min-width: 961px)`, `body:not(.folded)` + `#adminmenu`, `#adminmenuback`,
`#adminmenuwrap`, `#adminmenu li.menu-top`, `#adminmenu .wp-submenu` get
`width: Npx !important`, and `#wpcontent`/`#wpfooter` get `margin-left: Npx
!important`. Below 961px they emit nothing and core's width applies.

`maestro.css:485`'s `max-height: 160px` is an unrelated results-list bound. Do
NOT touch it — it is the same number by coincidence, which is exactly the trap.

**Both layers enforce the unfold**, and both must stay in step: `forceUnfold()`
in `maestro.js` (~L197) strips the classes and re-strips via `MutationObserver`,
and the CSS above is the defensive backstop for a frame where the class survives.

**The collapse control today** (UX-12, 1.5.3): hidden by CSS during edit mode,
with the capture-phase click guard in `forceUnfold()` kept as a functional
backstop. Out of scope here — see the objective.

**Why measure, not configure:** `forceUnfold()` has already stripped `.folded` /
`.auto-fold` by the time the toolbar is built, so the rendered `#adminmenuwrap`
width is the true expanded width from every source at once — core's 160px, a
Keel/PX override, or a future Maestro `menu_width`. A `ResizeObserver` keeps it
current when a breakpoint is crossed (Keel's rule switches on at 961px) or
another plugin previews a width change.
