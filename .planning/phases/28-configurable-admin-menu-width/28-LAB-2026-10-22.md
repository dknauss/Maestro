# Phase 28 local verification — 2026-10-22

Tested Maestro `4cea9a2` on an isolated WordPress 7.1.3 / PHP 8.3 wp-env
site, ports 8908/8909. Maestro and Keel were mounted directly from their
repositories. Keel 0.8.0 source: `ccd76b2d05a82016bfd87f0e2ec5e035dbf0efdd`
(clean checkout). Arabic core translations were installed for the RTL check.
Browser: installed Google Chrome, driven headlessly through Playwright.
No production sites or existing local site databases were changed.

## Confirmed

- Fresh, Modern, Midnight: widths 180, 240, 320px render at the requested width
  in browsing and edit mode (18 combinations). Settings reports the correct
  slider value. Screenshots were captured for all combinations; representative
  Fresh, Modern and Midnight screenshots were inspected.
- A stored 240px width does not override core's 36px auto-fold while browsing
  at 783, 900, or 960px. Edit mode unfolds to 160px at those widths; the resize
  handle is hidden. At 961px the stored 240px width and handle apply again.
- Real Arabic RTL admin: the menu is on the right. Shift+ArrowLeft grows it
  from 240 to 260px; Home restores 160px. This proves keyboard direction and
  width changes, **not complete RTL layout correctness** (see below).
- Real Keel, not the fixture: `admin_menu_width=200` wins over Maestro's stored
  240px while browsing and editing. Settings displays the 200px override notice;
  the handle's grow key leaves the rendered width at 200px.
- No browser page exceptions were recorded during the main matrix. The PHP
  debug log was empty during baseline verification.

## Confirmed defect: RTL toolbar is offset on the wrong side

At a 1280px viewport and 260px menu, the menu occupies x=1020..1280, but the
editor toolbar occupies x=260..1280. It should clear the right menu column,
not the left. The screenshot after Home also shows the toolbar extending
under the right menu while leaving a gap at the left.

`assets/maestro.css` lines 583–584 use `left: var(--maestro-menu-width)` and
`right: 0`, without an RTL override. The same rule exists at v1.6.0's release
commit `7d1f1d0`: this predates #228, but prevents a clean Phase 28 RTL sign-off.
Fix and verify toolbar edges at 160/240/320px in RTL, including settings
placement, before closing Phase 28.

## Follow-up fix and verification (same day)

The earlier results above describe the baseline at `4cea9a2`. This follow-up
supersedes its unresolved RTL finding and mobile verification gap:

- The toolbar now uses `inset-inline-start` / `inset-inline-end`; the mobile
  breakpoint resets inline-start to zero. This reserves the menu column on
  either side, with a full-width toolbar below 783px.
- The mobile settings dialog now belongs to `#adminmenuwrap`, like its toolbar,
  with fixed viewport positioning. Previously it was appended to body, so a
  real click in its input made core close the overlay as an outside click.
- Settings handles Escape on keyup before returning focus. It also consumes Tab
  keyup: core otherwise queues a focus check against a dialog input that can
  become detached if Escape immediately follows. This prevents closing the
  overlay after the dialog has already returned focus to Settings.
- Mobile visibility assertions now target `#adminmenu`, following the existing
  mobile suite. Testing the wrapper itself produced misleading visibility
  failures even when its menu and fixed toolbar were on screen.
