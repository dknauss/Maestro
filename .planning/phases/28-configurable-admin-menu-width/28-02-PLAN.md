<objective>
Store the width, and cross the line this feature actually turns on: applying it
while merely *browsing* wp-admin.

Purpose: every Maestro asset today is edit-mode-gated except
`maestro-admin-bar.css`. "Costs nothing unless you are editing" is currently true
and this plan is where it stops being — for every admin user, on every page load.
That is worth being deliberate and measured about rather than discovering in a
support thread.

**`autonomous: false`** — Task 1 carries a footprint decision that is the
user's to make.
</objective>

@includes/class-config.php
@includes/class-assets.php
@docs/performance/config-size-and-page-load.md

<interfaces>
<!-- Contracts the executor builds on. Use directly — no exploration needed. -->

`Config::sanitize()`'s established shape for a scalar: coerce → bound → drop when
it equals the default (sparse contract — a config that stores the default is
indistinguishable from one that never set it, and reset means "absent").

`Assets::enqueue()` currently returns early when `! is_edit_mode()`, after
enqueueing only `maestro-admin-bar.css`. The width rule has to be emitted BEFORE
that early return.

**Cheapest viable delivery, in order of footprint:**
1. An inline `<style>` on `admin_head` — no HTTP request, a few dozen bytes,
   emitted only when a non-default width is stored. Almost certainly right.
2. A tiny enqueued stylesheet — an extra request per page load, for one rule.
3. Extending an existing always-loaded file — couples unrelated concerns.

**The `docs/performance/config-size-and-page-load.md` baseline applies**: a
realistic config costs ~0.1 ms/page today, and `Config::get()` is a
non-autoloaded option, so reading it on every admin page is a new cost that
needs measuring — not the CSS, the OPTION READ.
</interfaces>
</context>

<tasks>

<task type="checkpoint">
  <name>Task 1: DECIDE the always-loaded footprint</name>
  <action>
    Two questions, both the user's:

    1. **Delivery.** Inline `<style>` (recommended — no request, tiny, trivially
       conditional) versus an enqueued file. Inline CSS is sometimes disliked on
       principle; here it is a single rule whose value comes from user config, and
       an extra HTTP request per admin page load to carry it is the worse trade.
    2. **The option read.** Applying width outside edit mode means reading
       `maestro_config` on every admin page for every admin user. It is a single
       non-autoloaded option and object-cache-backed, so the marginal cost should
       be near zero on a site with a persistent cache and one query without —
       but *should be* is not *is*. Measure before shipping, and decide whether a
       tiny autoloaded `maestro_menu_width` option is worth avoiding the read of
       the larger one.

    State the measured numbers at the checkpoint, not adjectives.
  </action>
  <verify><manual>Footprint decision recorded with measurements.</manual></verify>
  <done>Delivery mechanism and option strategy decided, with numbers.</done>
</task>

<task type="auto" tdd="true">
  <name>Task 2: Store and bound `menu_width`</name>
  <files>includes/class-config.php, tests/unit/ConfigSanitizeTest.php, TESTING.md</files>
  <behavior>
    - `menu_width` sanitizes to an integer within sane bounds; out-of-range clamps
      rather than rejecting the whole save.
    - The default (160) is NOT stored — sparse contract, reset = absent.
    - Non-numeric, negative and absurd values cannot reach storage.
    - Every existing config shape sanitizes byte-identically (zero regression).
  </behavior>
  <action>
    Pick the bounds deliberately and say why in the constant's docblock. A lower
    bound below roughly the folded width makes the menu unusable; an upper bound
    much past a third of a typical viewport starts eating the content column. The
    numbers matter less than the reasoning being recorded — the next person will
    otherwise assume they were arbitrary and change them.
  </action>
  <verify><automated>composer test:unit -- --filter ConfigSanitizeTest</automated></verify>
  <done>Bounded, sparse, zero-regression; bounds justified in the docblock.</done>
</task>

<task type="auto" tdd="true">
  <name>Task 3: Apply it outside edit mode</name>
  <files>includes/class-assets.php, tests/integration/MenuWidthAssetTest.php, TESTING.md</files>
  <behavior>
    - With a non-default width stored, the rule is emitted on ordinary admin pages.
    - With no width stored, NOTHING is emitted and no new work happens — the
      zero-config path stays exactly as it is today.
    - The rule sets `#adminmenu`/`#adminmenuwrap`/`#adminmenuback` width AND the
      matching `#wpcontent`/`#wpfooter` offset. Setting one without the other
      overlaps or gaps the content column.
    - `body.folded` still folds to core's 36px outside edit mode — width applies
      to the EXPANDED state only.
    - Below the `<782px` breakpoint the menu is an overlay; the width must not
      fight core's responsive rules.
  </behavior>
  <action>
    The folded and responsive cases are where this breaks in the wild, and both
    are cheap to assert. A width override that survives into folded mode disables
    the collapse control for every admin page — which is the bug this phase's
    own decision exists to avoid re-creating outside edit mode.
  </action>
  <verify><automated>npm run test:php -- --filter MenuWidthAssetTest</automated></verify>
  <done>Width applies while browsing; zero-config emits nothing; folded and responsive both still correct.</done>
</task>
