<objective>
Build the storage half: the `profiles` authoring map, and the compile step that
expands it onto the inline `hidden_profiles` axis.

Purpose: the feasibility note's whole architecture rests on profiles being an
authoring convenience that *compiles away*, so resolution stays in one seam.
If the map ever has to be consulted at resolve time, the design has failed — and
this plan is where that property is established or lost.
Output: sanitize accepts profiles, compiles them, and leaves the existing axes
untouched.
</objective>

<interfaces>
<!-- Contracts the executor builds on. Use directly — no exploration needed. -->

Follow `Config::sanitize()`'s established axis shape exactly:
guard `! empty && is_array` → coerce members → intersect against what is LIVE →
cap → assign ONLY when non-empty (sparse: reset = absent key).

`hidden_users` is the closest model — read it before writing `hidden_profiles`.

**The compile is the load-bearing part.** `profiles` is authoring; the stored
`items[slug].hidden_profiles` is what replay reads. Both are persisted, but only
the compiled axis is ever resolved from. Getting this backwards — resolving from
the map — reintroduces the second lookup path §5b was rejected for.

**Zero-regression is not optional.** `ConfigSanitizeTest` already has
`test_role_only_config_is_unchanged_by_the_user_axes`, added when the user axes
landed for exactly this reason. Add its profiles analogue: a config carrying only
role and user axes must sanitize byte-identically after this plan.

**Authorization**, if 27-01 decided profiles need it: `protected_user_axes()` is
the pattern — reject-on-add, and preserve rather than destroy for a saver without
authority. Note the lesson recorded there: that protection took four attempts
because it was three mechanisms instead of one. If profiles need the same, build
it as ONE map keyed by normalized slug from the start.
</interfaces>

<task type="auto" tdd="true">
  <name>Task 2: Compile profiles onto the inline axis</name>
  <files>includes/class-config.php, tests/integration/ProfilesCompileTest.php, TESTING.md</files>
  <behavior>
    - Saving a profile that hides slugs A and B writes `hidden_profiles` containing
      that profile's name onto items A and B.
    - Removing a slug from the profile removes it from that item's axis on the next
      save; emptying the axis drops the key (sparse).
    - Deleting a profile leaves no dangling reference that RESOLVES — whether it is
      cleaned at compile time or self-heals at resolve time is 27-01's decision,
      but the test asserts whichever was chosen.
    - The compile is deterministic and idempotent: sanitizing an already-compiled
      config twice produces identical output.
    - Compiled items respect `MAX_ITEMS`; a profile naming more slugs than remain
      does not silently evict other overrides.
  </behavior>
  <action>
    Idempotence matters more than it looks: the editor autosaves a FULL REPLACE,
    so this runs on every save, repeatedly, over its own prior output. A compile
    that is not idempotent produces drift that only shows up after N saves.

    The MAX_ITEMS interaction is the same shape as the starvation bug the v1.5.0
    ultrareview found in the per-user path — reserve or bound deliberately rather
    than discovering it later.
  </action>
  <verify><automated>npm run test:php -- --filter ProfilesCompileTest</automated></verify>
  <done>Compile is correct, idempotent, bounded, and asserted against MAX_ITEMS.</done>
</task>
