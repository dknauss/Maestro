**ALREADY BUILT by Phase 21 — this phase extends, it does not rebuild:**

- `Replay::is_hidden_for_current_user()` is already independent OR'd terms with a
  comment reserving the slot: **`class-replay.php:510`, "Term 3 —
  hidden_profiles … slots in here"**. That reservation was the point.
- `Replay::resolved_override_list( $field, … )` is field-parameterized, so a
  `hidden_profiles` axis inherits the qualified-key, schema-v2 and Axis-1/Axis-2
  guards from ONE implementation. Do not add a parallel resolver.
- `Config::sanitize()` has an established shape for a bounded list axis:
  guard → coerce → intersect-against-live → cap → sparse-drop-when-empty.
- `Config::protected_user_axes()` shows the pattern for an axis that a saver may
  lack authority to write.

**LOCKED by the feasibility note §7 — do not re-litigate:**

- A `profiles` top-level map is the AUTHORING structure; it **compiles** at save
  time onto `items[slug].hidden_profiles: [profile-name]`.
- Resolution stays entirely inside `is_hidden_for_current_user()`. The `profiles`
  map is consulted ONLY to resolve *live membership* — never as a second place
  hiding resolves from. One lookup, one seam, one audit point.
- Membership is intersected LIVE each request (self-healing, §4).
- A profile is Maestro-internal bookkeeping. It never calls `add_role()`/`add_cap()`,
  never appears in `wp_roles()`, never changes `$user->roles`.

**OPEN — this plan decides:** everything about how a human creates, names,
assigns and deletes a profile.

<task type="checkpoint">
  <name>Task 1: Decide the authoring UX</name>
  <action>
    **PARTLY ANSWERED 2026-08-10 — see `.planning/DECISION-settings-surface.md`.**
    Profiles are created, renamed, deleted and have their membership edited in a
    **Profiles modal**, opened from a new icon in the toolbar's right zone (the
    zone that already hosts Reset All, the one existing menu-wide action).
    ASSIGNING a profile to an item stays in the visibility popover as a fifth
    group, because assignment is per-item and belongs beside the other axes.
    There is no wp-admin settings page.

    What remains for this task is the detail INSIDE that frame:

    The visibility popover is already at FOUR groups after Phase 21. A fifth
    ("Hide for profile") is cheap to add, but profiles also need somewhere to be
    *created and managed*, and that has no home today — Maestro has deliberately
    never had a settings screen ("no separate settings screen" is in the core
    value statement).

    Questions that need answers, each with a real trade-off:

    1. ~~Where do profiles get authored?~~ **Decided** — see above. Remaining
       sub-question: can a profile be created *inline* from the assignment group
       as a shortcut, or must every creation go through the modal? A shortcut is
       convenient and is a second creation path to keep consistent.
    2. **What is a profile's assignment?** The note's §5c shape allows both users
       AND roles under one profile. Roles-in-profiles overlaps confusingly with
       the existing `hidden_roles` axis — worth asking whether v1 profiles should
       be users-only for clarity, with roles deferred.
    3. **Does the popover show which profiles hide an item, or only let you add
       one?** Showing them means resolving profile→item backwards for display.
    4. **What happens on delete?** A profile referenced by `items[].hidden_profiles`
       that no longer exists must self-heal (the §4 invariant says it will), but
       the editor should probably say so rather than silently dropping rules.
    5. **Is there a cap?** `MAX_HIDDEN_ROLES`/`MAX_HIDDEN_USERS` are both 50. A
       profile count cap and a per-profile membership cap both need numbers.

    Recommend, do not just enumerate — but the human decides.
  </action>
  <verify><manual>Decisions recorded in 27-CONTEXT.md with rejected alternatives.</manual></verify>
  <done>Authoring UX locked, with reasoning.</done>
